Type-driven design  ·  Core principles

Making illegal states unrepresentable

A design principle that moves the burden of correctness from runtime checks and programmer discipline to the structure of types themselves.

Every program carries two models of its domain: the one written in code, and the one that is actually true. In most codebases, these two models diverge. The code says a User has an email: string and an isVerified: boolean — but the domain says something subtler: an unverified user has an unconfirmed address, and a verified user has one that has been checked. The boolean is a compression of that reality, and compressions lose information. Lost information becomes bugs.

Making illegal states unrepresentable is the discipline of closing that gap — not through more careful code, but through more expressive types. If the type system cannot construct a value that violates your domain rules, those violations cease to be a runtime possibility. They become, instead, a compile-time impossibility.

The problem with flags

Consider how a naïve model of "email verification" typically looks in a dynamically or weakly typed system:

Fragile model
type User = {
  email: string
  isVerified: boolean
}
All of these compile
// ✓ sensible
{ email: "a@b.com", isVerified: true }

// ✓ sensible
{ email: "a@b.com", isVerified: false }

// ✗ nonsense — compiles fine
{ email: "", isVerified: true }

The type permits nonsense. You can have a verified user with no email, or an empty string that downstream code — trusting isVerified — will treat as legitimate. The compiler waves it through. Every function that receives a User must now silently wonder whether it can trust the flag. The question becomes a constant, invisible tax on every callsite.

Now redesign the type to reflect the actual domain:

Expressive model
type User =
  | { status: "unverified"; email: string }
  | { status: "verified";   verifiedEmail: string }

// A function that only accepts verified users
function sendConfirmation(user: Extract<User, { status: "verified" }>) {
  // verifiedEmail is guaranteed present — no check needed
  send(user.verifiedEmail)
}

The impossible state — a verified user with no email — can no longer be constructed. The compiler enforces it. There is no boolean to misread, no empty string to guard against, no runtime check to forget. The type carries the proof that the contract has been satisfied.

Parse, don't validate

Closely related — and often described as the runtime counterpart of this principle — is the distinction between parsing and validating. Validation is a function that returns a boolean: it answers "is this data acceptable?" Parsing is a function that returns a new type: it answers "here is the acceptable version of this data, or an error explaining why it doesn't exist."

Validation: proves nothing
function isValidEmail(s: string): boolean

// Caller must remember to check,
// and the type is still `string`
// after the check passes.
Parsing: proof in the type
function parseEmail(s: string)
  : Email | Error

// If you have an `Email`, it was
// validated at construction.
// No re-checking needed downstream.

The key insight is where this happens. Parsing occurs once, at the boundary where untrusted data enters the system — an HTTP request, a file read, a form submission. Everything inside the system speaks in already-parsed types. The proof that the data is valid is encoded in the type itself, not in a flag, not in a comment, not in programmer memory. It travels with the value wherever it goes.

The boundary principle

Draw a line around your system's trust boundary. Untrusted data — strings, JSON, user input — crosses that boundary exactly once. At the crossing, you parse it into domain types. Inside the boundary, no function ever re-validates data that a type already guarantees. This is where the principle actually delivers its value: not at the moment of parsing, but in the thousands of callsites that never have to think about it again.

How far it goes

The principle scales with your type system's expressiveness. In TypeScript you can get remarkably far with discriminated unions and branded types. In Haskell or Rust, phantom types let you encode state machine transitions — a Connection<Open> type that literally cannot be passed to a function expecting Connection<Closed>. In languages with dependent types (Idris, Lean), you can encode that a list has a specific length, that an index is always within bounds, that a matrix multiplication has compatible dimensions — all at compile time, with no runtime overhead.

A classic example is modeling a non-empty list. The standard List<T> forces every caller of head() to handle the empty case — or risk a runtime crash. A NonEmptyList<T> type, constructed only when you have at least one element, makes head() total: it always returns a value, because the type guarantees there is one.

Haskell — phantom types for connection state
data Open
data Closed

newtype Connection state = Connection Handle

open  :: String -> IO (Connection Open)
close :: Connection Open -> IO (Connection Closed)
query :: Connection Open -> Query -> IO Result

-- query on a closed connection: compile error, not runtime crash

The pragmatic limit is also real. Encoding every invariant as a type is not free — it requires a richer type vocabulary, steeper onboarding for new contributors, and sometimes machinery (type class instances, GADTs, proof terms) that can obscure simple logic. The art is in calibrating how much of the domain to encode. Illegal states that are catastrophic, security-relevant, or frequently violated by accident are worth encoding. States that are merely improbable or easily caught by tests may not justify the complexity.

What changes in practice

The most immediate effect is that function signatures become documentation that cannot go stale. A function that takes a VerifiedUser communicates its precondition exactly, without a comment, without a runtime assertion, without a unit test that checks the check. The type does the work. Readers don't need to trace through the implementation to understand what is assumed — the contract is visible at the callsite.

The compounding effect comes over time. As a codebase grows, the surface area of invalid states grows with it. In a weakly-typed system, that surface area is managed by tests, conventions, code review, and memory. All of these scale poorly. Types scale perfectly: adding a new field that must be present in the verified state means adding it to the type, and the compiler tells you every callsite that needs to be updated. The refactoring is guided rather than hunted.

Function signatures become documentation that cannot go stale. The type does the work.

Perhaps most importantly, it changes the texture of reading code. Functions that operate deep inside a system — far from any input validation — no longer need to be read defensively. When a type guarantees a precondition, the function body can assume it without apology. The mental overhead of wondering "but what if this is empty, or null, or unverified" disappears because the type has already answered the question. You read the code at face value, and face value is correct.
